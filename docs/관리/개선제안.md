# 개선 제안

3단계를 하면서 실제로 찾은 것과, 아직 안 한 것을 우선순위대로 적는다.
추측이 아니라 돌려보고 나온 것만 근거로 삼았다.

## 1. 이번에 고친 것

### 로컬과 운영이 갈라지는 문제

가장 많이 나온 부류다. compose 파일이 두 개(base + rds)인데, 그걸 안 따라가는
자리가 네 군데 있었다. 전부 같은 증상으로 이어진다 — **앱이 RDS 를 버리고
빈 컨테이너 DB 를 보게 된다.**

| 자리 | 무슨 일이 났을까 |
|---|---|
| `deploy.yml` | main 에 푸시할 때마다 RDS 를 떠난다 |
| 워치독 | 복구가 돌면 없어야 할 Postgres 컨테이너를 새로 만든다 |
| `Makefile` | 서버에서 `make up` 한 번이면 같은 일이 난다 |
| 운영매뉴얼 백업 | `exec -T db` 를 쓰는데 RDS 모드엔 `db` 서비스가 없다. 백업이 통째로 실패한다 |

`/etc/stockcast.env` 에 조합을 한 번 적어 두고 네 곳이 모두 그걸 읽게 했다.
설정을 여러 곳에 손으로 복사하면 언젠가 한 곳이 뒤처진다.

### 접속 주소가 조용히 로컬로 떨어지던 문제

`docker-compose.rds.yml` 에서 `${DATABASE_URL:?}` 로 안전장치를 걸었는데 안 걸렸다.
`.env` 에 이미 로컬용 `DATABASE_URL`(localhost)이 있어서 "값이 있으니까" 통과한 것이다.
컨테이너가 자기 자신의 `localhost:5432` 로 붙으러 갔다.

이름을 `RDS_DATABASE_URL` 로 분리해서 안 채우면 기동 자체가 멈추게 했다.
**안전장치는 걸어 두는 게 아니라 걸리는지 확인해야 한다.**

### 웹 계층 취약점 9건

`pip-audit` 로 확인했다.

| 패키지 | 전 | 후 | 건수 |
|---|---|---|---:|
| starlette | 0.38.6 | 1.6.0 (fastapi 0.141.1 이 끌어온다) | 9 |
| pytest | 8.3.2 | 9.1.1 | 1 |
| python-dotenv | 1.0.1 | 1.2.3 | 1 |

starlette 은 인터넷에 노출된 웹 계층이라 우선순위가 높았다.
격리된 venv 에 올려 테스트 75개를 통과시킨 뒤에 반영했고, 다시 스캔해서
`No known vulnerabilities` 를 확인했다.

### TLS 를 우회할 수 있던 구성

Caddy 가 443 에 인증서를 붙여 두는데, 보안그룹이 **8000 과 8069 를 전 세계에**
열어 두고 있었다. `http://<공인IP>:8000` 으로 그냥 붙어지고 그 트래픽은 암호화가 없다.
인증서를 걸어 놓고 옆문을 열어 둔 셈이다. 8069(Odoo)는 로그인 폼이 있어서 더 나쁘다.

둘 다 기본을 내 IP 로만 열게 바꿨다. 공개해야 하면 `open_app_port` 를 켠다.

### DB 가 멎으면 앱 전체가 멎던 문제

`connect_timeout` 이 없어서, 붙을 수 없는 DB 를 만나면 요청이 안 끝났다.
그동안 워커가 다 물리고 헬스체크까지 죽어서, 워치독이 재시작을 반복하게 된다.

측정해 보니 **5.1초에 끊긴다.** 예전 설정은 30초가 지나도 안 끝났다.
`statement_timeout=30s` 와 `pool_recycle=300` 도 함께 걸었다. RDS 는 네트워크
너머라 유휴 연결이 조용히 끊기는데, 로컬 컨테이너일 때는 티가 안 나던 것들이다.

### 백업 스크립트가 문서에만 있던 문제

운영매뉴얼이 `scripts/backup.sh` 를 가리키는데 **그 파일이 없었다.**
두 모드를 모두 처리하게 만들고, `--verify` 를 붙이면 임시 컨테이너에 실제로
복원해서 테이블 수와 재고 정합성까지 확인하게 했다.

같은 매뉴얼에 "복원해본 적 없는 백업은 백업이 아니다"라고 적어 두고 정작
복원해 본 적이 없었다. 이번에 돌려서 18개 테이블·10,010행이 되살아나는 걸 봤다.

## 2. 아직 안 한 것 — 먼저 할 순서대로

### 2-1. 비밀값을 코드 밖으로 — **코드 작성 완료, 적용 전**

지금 `user_data` 가 `.env` 를 평문으로 만든다. API 키 4개와 DB 비밀번호가 들어간다.
이 값은 **인스턴스 메타데이터로 읽힌다.** EC2 안에서 도는 아무 프로세스나
`http://169.254.169.254/latest/user-data` 로 꺼낼 수 있다.

`terraform.tfstate` 에도 DB 비밀번호가 평문으로 있다. `.gitignore` 로 막아 뒀지만
파일 자체는 평문이다.

**SSM Parameter Store** 로 옮기는 게 맞다. 이번에 만들어 뒀다. `SecureString` 은 표준 파라미터라면
무료고, EC2 에 인스턴스 역할을 붙여 부팅할 때 읽어 오게 하면 된다.
그러면 user_data 에는 "어느 파라미터를 읽어라"만 남는다.

만든 것은 이렇다.

| 파일 | 하는 일 |
|---|---|
| `infra/terraform/ssm.tf` | EC2 역할·인스턴스 프로파일, `/stockcast/*` 만 읽는 최소 권한 |
| `scripts/put_secrets.sh` | `.env` 값을 SecureString 으로 넣는다. 값은 마스킹해서 보여준다 |
| `user_data` | `use_ssm = true` 면 부팅할 때 SSM 에서 꺼내 온다 |

파라미터를 terraform 이 만들지 않는 게 핵심이다. terraform 이 만들면 값이
tfstate 에 평문으로 남아서 옮긴 의미가 절반으로 준다. 값은 스크립트로 넣고
terraform 은 읽기만 한다.

양쪽 모드로 렌더링해서 확인했다. `use_ssm = true` 로 렌더한 user_data 에는
비밀값이 하나도 안 들어간다.

남은 한 가지는 RDS 비밀번호다. `data "aws_ssm_parameter"` 로 읽어도 데이터 소스는
tfstate 에 저장되므로 거기엔 남는다. 완전히 빼려면 RDS 의
`manage_master_user_password` 를 쓰면 되는데 Secrets Manager 라 월 $0.40 이 붙는다.
지금은 안 켰다.

**적용은 아직 안 했다.** `./scripts/put_secrets.sh --apply` 로 값을 넣고
`use_ssm = true` 로 바꾸면 된다.

### 2-2. Terraform 상태를 원격으로 — **코드 작성 완료, 적용 전**

지금은 `terraform.tfstate` 가 로컬 파일 하나다. 문제가 두 가지다.

- **잠금이 없다.** 두 곳에서 동시에 apply 하면 상태가 깨진다
- **날아가면 끝이다.** 상태를 잃으면 terraform 이 기존 리소스를 모른다.
  실제로 이번에 상태와 실제 AWS 가 어긋나 있는 걸 겪었다 — 상태에는 EC2·EIP·SG 가
  있는데 AWS 에는 없었다

`infra/terraform-bootstrap/` 에 만들어 뒀다. S3 버킷(버전 관리·암호화·공개 차단·
90일 후 옛 버전 정리)과 DynamoDB 잠금 테이블을 만든다. 상태를 담을 곳을 만드는
코드라 자기 자신은 로컬 상태를 쓴다.

옮기는 순서는 `infra/terraform/backend.tf.example` 에 적어 뒀다.
버킷이 없는 상태로 backend 블록을 넣으면 init 이 실패하므로 순서가 중요하다.

S3 는 몇 KB짜리 파일 몇 개라 사실상 0원이고, DynamoDB 는 온디맨드라
apply 할 때만 몇 건 읽고 쓴다.

### 2-3. CI 에서 잡을 수 있는 것들 (우선순위 중간)

지금 CI 는 pytest 만 돌린다. 이번에 손으로 찾은 것들은 전부 CI 가 잡을 수 있다.

| 추가할 것 | 이번에 이걸로 찾았을 것 |
|---|---|
| `pip-audit` | starlette 취약점 9건 |
| `terraform validate` + `fmt -check` | 보안그룹 description 에 한글 못 쓰는 것 |
| `ruff check` | 예외 체인 누락 3건, 미사용 import 3건 |
| `docker compose config` (두 모드) | RDS 오버레이가 깨지는 것 |

특히 마지막이 값어치가 크다. compose 두 조합이 모두 유효한지 CI 가 매번 확인하면,
이번에 찾은 부류의 버그가 다시 들어오지 못한다.

### 2-4. 로그가 재시작하면 사라지는 문제 (우선순위 중간)

`/api/ops/logs` 는 메모리 링버퍼다. 컨테이너가 재시작하면 없어진다.
**장애 원인을 봐야 할 바로 그때 사라진다.** 워치독이 앱을 재시작하고 나면
왜 죽었는지 볼 방법이 없다.

CloudWatch Logs 로 보내면 되는데 수집 요금이 붙는다(GB당). 로그 양이 적으니
크지 않지만, 최소 비용 기조라면 우선 호스트 파일로 남기고
`logrotate` 로 도는 것부터 해도 된다.

### 2-5. 서버가 한 대인 것 (우선순위 낮음 — 지금 구성에서는)

인스턴스가 죽으면 서비스가 멈춘다. 워치독과 CloudWatch 복구로 되살리는 시간은
줄였지만 0은 아니다.

제대로 하려면 ALB + Auto Scaling Group 인데, ALB 하나가 월 $16 이상이라
지금 전체 비용($33.93)의 절반이다. **이 프로젝트 규모에서는 과하다.**
DB 를 RDS 로 뺐으니 인스턴스가 날아가도 데이터는 남는다는 것으로 충분하다고 본다.

굳이 한다면 ASG min=max=1 만 걸어도 인스턴스 소실에는 대응된다. ASG 자체는 무료다.
다만 EIP 재연결과 부팅 시간(현재 user_data 기준 수 분)을 감수해야 한다.

## 3. 인프라 직무로 지원할 때 무엇을 말할 수 있나

이 프로젝트에서 실제로 한 것 중 이야기가 되는 건 이런 것들이다.

**설정이 갈라지는 걸 구조로 막았다.** compose 파일 조합을 한 곳(`/etc/stockcast.env`)에
두고 배포·워치독·Makefile·운영매뉴얼이 모두 그걸 읽게 했다. 처음엔 네 군데가
제각각이었고, 그대로 뒀으면 배포할 때마다 DB 가 바뀌는 사고가 났을 것이다.

**안전장치가 실제로 걸리는지 확인했다.** `${DATABASE_URL:?}` 를 걸어 두고
안심했는데 안 걸렸다. 값이 있었기 때문이다. 걸어 두는 것과 걸리는 것은 다르다.

**복구를 증명 가능한 방식으로 확인했다.** 워치독을 `docker kill` 로 시험하면
재시작 정책도 같은 일을 해서 무엇이 살렸는지 알 수 없다. `docker pause` 로
얼려서 — 재시작 정책이 못 고치는 상황을 만들어 — 워치독만 살릴 수 있는 걸 봤다.

**비용을 근거로 정했다.** AWS Pricing API 에서 실단가를 받아 구성별로 계산했고,
t4g(ARM)로 20% 줄이면서 쓰는 이미지 다섯 개가 arm64 를 지원하는지 먼저 확인했다.

**옮기기 전에 데이터를 의심했다.** 마이그레이션 후 정합성이 깨져 보였는데,
행 수는 18개 테이블 전부 맞았다. 원인은 3개월 전 시더의 버그였고 데이터가
원래 그랬다. 행 수가 맞는 것과 데이터가 맞는 것은 다르다.

부족한 건 2절에 적은 것들이다. 특히 비밀값 관리와 원격 상태는
"알고 있지만 이번 범위에서 안 했다"로 말할 수 있어야지, 모르고 지나간 걸로
보이면 안 된다.
