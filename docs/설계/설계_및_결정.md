# 설계와 기술적 판단

만들면서 뭘 고민했고 왜 그렇게 정했는지 정리했다. 운영 절차(점검·장애대응·백업)는
[유지보수_운영매뉴얼.md](../운영/유지보수_운영매뉴얼.md)에 따로 있다.

---

## 1. 어떤 업무를 다루나

공공조달 납품업체의 내부 운영 시스템이다. 고객이 쓰는 화면은 없고 재고·조달·
수요예측·설비·경영분석 같은 관리 업무만 다룬다.

취급 품목 30종은 조달청과 나라장터에 실제로 있는 카테고리에서 골랐다. 제설·방재,
안전·보호구, 냉난방, 사무, 청소·위생, 방역·보건, 제초·조경, 전기·조명 여덟 가지다.
이렇게 잡아야 외부 공공데이터가 도메인과 맞아떨어진다. 나라장터 입찰은 실수요고,
조달청 단가는 실가격이고, 기상청 날씨는 계절 수요를 설명한다.

---

## 2. 운영계와 분석계를 나눈 이유

- **Odoo 18** — 실물 재고와 입출고, 재주문 규칙을 담당한다. 지금 이 순간의 재고는
  Odoo가 정답이다.
- **StockCast** — 1년치 거래 이력과 외부 공공데이터를 모아 수요예측·안전재고·
  경영분석을 한다.

둘은 XML-RPC로 오간다. StockCast가 계산한 재주문점과 발주상한을 Odoo 재주문
규칙에 써넣고, 반대로 Odoo의 실재고를 읽어 대시보드에 띄운다.

DB를 굳이 두 개로 나눈 건 세 가지 때문이다. 외부 데이터를 Odoo에 저장할 자리가
없는데 예측은 출고량과 날씨를 조인해야 나온다. 무거운 분석 쿼리를 운영 DB에
돌리면 현장 입출고가 느려진다. 그리고 조회할 때마다 Odoo에서 1년치를 끌어와
회귀를 돌리는 건 현실적이지 않다.

## 3. 기술 선택

| 기술 | 고른 이유 |
|------|----------|
| FastAPI | OpenAPI 문서가 자동으로 나오고 pydantic 타입 검증이 붙어 있다 |
| SQLAlchemy 2.0 | ORM으로 DB를 갈아끼울 수 있다(운영 PostgreSQL / 테스트 SQLite). merge로 멱등 upsert |
| PostgreSQL 16 | 무난한 표준 RDB. 테스트는 SQLite 인메모리로 돌린다 |
| Odoo 18 Community | 무료인데 진짜 ERP다. 자체 호스팅이라 API 제약이 없다 |
| statsmodels | 계수·p-value·R²를 볼 수 있어서 "기온 1℃당 출고 X개"를 뽑아낼 수 있다 |
| React + Chart.js 단일 HTML | 빌드 도구 없이 백엔드가 그냥 서빙한다. 인프라가 단순해진다 |
| Docker / Terraform / Caddy | 환경 일관성, 코드로 된 인프라, 자동 HTTPS |

차별점은 명확하다. Odoo는 AI와 수요예측이 Enterprise 유료판 전용이라, 그 자리를
StockCast가 무료로 채운다.

## 4. 데이터 모델

### 왜 SAP 구조를 흉내 냈나

재고관리 토이 프로젝트는 대개 `상품(수량)` 테이블 하나에 숫자를 더하고 빼는
식으로 끝난다. 그런데 실무 ERP는 그렇게 안 한다. 재고 수량을 직접 고치지 않고,
입출고를 자재문서로 기록한 다음 재고는 그 결과로 집계한다.

이렇게 하면 감사 추적이 남는다. 언제 무엇이 왜 움직였는지가 전부 기록되니 재고가
이상해도 원인을 찾을 수 있다. 출고 이력이 그대로 수요 시계열이 되는 것도 덤이다.
그리고 `Σ(방향×수량) = 재고`라는 검증 가능한 등식이 생긴다. 이건 운영 화면의
정합성 점검 C01이 계속 확인한다.

부수적으로, SAP를 쓰는 회사 담당자에게 "MARA/MARD/MKPF/MSEG를 차용했다"고 하면
설명이 한 번에 끝난다.

컬럼명은 영문 의미명으로 쓰되 원본 SAP 필드명(MATNR, BUDAT 같은)을 주석에 달아뒀다.
MATNR, LABST 같은 약어만 쓰면 나중에 나도 못 알아본다.

### 엔터티 구성

| 분류 | 엔터티 | SAP 대응 |
|------|--------|---------|
| 마스터 | `plant` · `storage_location` · `material` | T001W · T001L · MARA+MAKT |
| 코드성 | `material_group` · `movement_type` · `ext_holiday` | T023 · BWART |
| 거래 | `material_doc_header` · `material_doc_item` | MKPF · MSEG |
| 재고/현황 | `stock` · `nfc_tag` | MARD |
| 이력성 | `stock_snapshot_history` | — |
| 외부 공공데이터 | `ext_weather` · `ext_bid_notice` · `ext_shop_price` · `ext_retail_index` | — |
| 설비 유지보수 | `equipment` · `maintenance_order` · `maintenance_order_part` | EQUI+EQKT · AUFK/AFIH · RESB→MSEG |

외부 공공데이터는 FK로 묶지 않고 분석할 때 날짜로 조인한다.

멀티테넌트(`tenant_id`)는 일부러 안 넣었다. "SaaS 트렌드는 지났으니 단일 기업
백오피스에 집중하라"는 피드백을 받아서다. 조직 구조는 플랜트/저장위치 2단계면
충분하다.

Oracle DDL은 `db/oracle/stockcast_oracle_schema.sql`에 있다. 모델링 툴에서
리버스 엔지니어링할 때 쓴다.

## 5. 공공데이터 커넥터

네 개를 붙였다.

1. 기상청 ASOS 일자료 — 일 기온·강수
2. 한국천문연구원 특일정보 — 공휴일. 같은 날짜에 두 개가 오면(5/5 어린이날과
   부처님오신날처럼) 이름을 합쳐서 dedup 한다
3. 조달청 나라장터 입찰공고 — 조회기간이 한 달로 제한돼서 최근 30일만 받는다
4. 조달청 종합쇼핑몰 MAS — 실 계약단가

여기에 통계청 KOSIS 소매판매액지수를 선택적으로 붙일 수 있다.

네 개 다 같은 원칙으로 짰다. HTTP 호출부와 파싱부를 분리해서 파싱만 단위 테스트할
수 있게 했고, `merge`로 멱등하게 넣고, 키가 없으면 그냥 건너뛰고 안내만 한다.
키 없이도 시스템이 돌아가야 하니까.

`scripts/collect_real_data.py`가 날씨·공휴일을 먼저 넣고, 그다음 거래를 실제
날씨·공휴일에 반응하도록 생성한다. 커넥터 하나가 죽어도 rollback 후 계속 진행해서
품목·거래 같은 핵심 데이터는 항상 완성된다.

한 가지 솔직히 말하면, 개별 판매 트랜잭션은 구할 수 없어서 수요량 자체는 모델로
만든 값이다. 대신 입력으로 실제 기온·강수·휴일을 넣어 반응시켰고, 단가는 조달청
실계약가, 입찰은 나라장터 실공고를 쓴다. 실데이터에 반응하는 시뮬레이션이라고
보면 된다.

## 6. 분석 엔진

### 신호가 있는지 먼저 확인했다

모델을 만들기 전에 출고 실적과 외부 변수 사이에 쓸 만한 신호가 실제로 있는지부터
봤다. 없으면 회귀를 돌릴 이유가 없다. 이때 출고(이동유형 201)만 집계하는 게
중요하다. 입고는 수요가 아니다.

기온과 일별 출고량의 상관계수(Pearson r)는 이렇게 나왔다.

| 구분 | 품목 | r | 해석 |
|------|------|---|------|
| 난방형 | 전기 온풍기 / 방한 안전작업복 / 산업용 전기히터 | −0.93 ~ −0.90 | 기온 내려가면 출고 늘어남 |
| 냉방·조경형 | 산업용 선풍기 / 이동식 에어컨 / 제초제 / 예초기 날 | +0.93 ~ +0.92 | 기온 올라가면 출고 늘어남 |
| 무관 | A4 복사용지 / 토너 카트리지 / LED 투광등 | −0.01 ~ +0.02 | 계절과 상관없음 |

계절 품목은 상관이 아주 강하게 나와서 회귀가 잡아낼 신호가 충분했다. 동시에
사무용품은 0에 가까운데, 이게 오히려 중요한 발견이었다. 모든 품목에 날씨를
집어넣으면 안 된다는 뜻이기 때문이다. 품목 특성에 맞는 변수를 골라야 한다.

주말·공휴일에는 전 품목 출고가 30% 정도 늘어서 `is_weekend`, `is_holiday`를
회귀에 넣었다.

`backend/tests/test_analytics.py`가 피처 생성(입고 제외)과 상관 부호(난방 음수,
냉방 양수)를 테스트로 고정해뒀다.

### 수요예측

**다중회귀(OLS)** — 종속변수는 일별 출고량, 독립변수는 기온·강수·주말·공휴일이다.
정확도보다 해석이 목적이다. 계수를 그대로 읽어서 발주 근거로 쓴다. 분산이 0인
변수가 있으면 통계값이 NaN이나 Inf가 되는데, 이러면 JSON 직렬화에서 터지므로
None으로 바꿔둔다.

**시계열** — Holt-Winters(주간 계절성, MAPE 같이 계산)와 SARIMA(1,1,1)(1,0,1)₇를
붙였다. `/api/forecast/{자재}/timeseries?method=` 로 둘 중에 고를 수 있게 해서
비교가 가능하다. 외부 변수가 필요 없어서 날씨 예보를 못 구할 때 쓸 수 있다.

### 재고·경영 지표

안전재고 `SS = Z·σ·√L`, 재주문점 `ROP = d̄·L + SS`, 발주상한 `S = d̄·(L+R) + SS`.
여기에 ABC 파레토, 재고회전율, 결품률, 재고자산금액을 얹었다.

## 7. Odoo 연동

인증(common)으로 uid를 받고 object/execute_kw로 실행한다. 백엔드 컨테이너에서
Odoo로 갈 때는 `host.docker.internal:8069`를 쓰는데, 리눅스에서는 compose의
`extra_hosts: host-gateway`가 필요하다.

붙이면서 걸린 것들이 몇 개 있다. 검색 도메인을 이중으로 감싸면 안 되고,
`action_apply_inventory`처럼 None을 반환하는 메서드는 XML-RPC 직렬화가 안 돼서
quant 수량을 직접 설정하는 방식으로 우회했다. Odoo 18에서 저장 가능한 품목은
`type=consu` + `is_storable` 조합이어야 한다.

## 8. 나중에 붙인 운영 기능

### 설비 유지보수

물류센터에서 지게차나 컨베이어가 멈추면 입출고 처리량이 그대로 멈춘다. 설비
가동률이 재고 회전의 선행지표라는 뜻이다. 자산관리 시스템이라면 물건 재고와
설비 상태를 같은 화면에서 봐야 한다고 판단했다.

MM과 이어지는 지점이 하나 있다. 정비오더를 완료하면 사용한 부품이 이동유형 261로
자재문서에 전기돼서 재고가 실제로 줄어든다. 기존 MM 전기 로직
(`post_goods_movement`)을 그대로 재사용했기 때문에 재고가 모자라면 완료가 409로
막힌다. 정비 부품이 장부 없이 사라지는 일이 없다.

지표는 가동률, PM준수율, MTTR, 정비비용(인건비+부품)을 낸다. 고장(CM)을 접수하면
설비가 자동으로 고장 정지 상태가 돼서 가동률에 바로 반영되고, PM을 완료하면
최근 정비일이 갱신돼 다음 주기가 다시 계산된다.

### 운영 관리

PoC는 "일단 돌아간다"까지지만, 운영은 "지금 정상인지 어떻게 아느냐"부터 시작한다.

- `/api/ops/health` — DB에 `SELECT 1` 왕복, Odoo XML-RPC 인증, LLM 가용성,
  디스크·메모리·Load, 요청 통계를 본다. healthy / degraded / down 세 단계로
  판정하는데, 이 응답을 자동 복구 스크립트도 똑같이 쓴다.
- `/api/ops/integrity` — 9개 항목을 검사한다. 몇 건 틀렸다고만 하면 쓸모가 없어서
  조치 방법과 실제 위반 샘플까지 같이 준다. 핵심은 C01 `자재문서 합계 = 재고`다.
- `/api/ops/logs` — 미들웨어가 경로·상태코드·소요시간을 메모리 링버퍼(500건)에
  쌓는다. 크기가 고정이라 메모리가 새지 않고, 재시작하면 비워지는 건 의도한 거다.
  오래 보관해야 하면 CloudWatch Logs로 바꾸면 된다.
- `/api/ops/stats` — 테이블별 행 수와 외부 데이터 최신성.

### 챗봇

`ai_insight`와 같은 방식으로 짰다.

질문이 오면 먼저 의도를 분류(9종)하고, 그 의도에 필요한 데이터만 DB에서 조회한다.
전체를 매번 넣으면 프롬프트가 커져서 로컬 Ollama가 확 느려진다.

LLM에게 DB를 직접 열어주지는 않는다. 서버가 조회한 수치만 컨텍스트로 넘기고
"없는 값은 지어내지 말라"고 명시한다. 환각도 막고 권한도 통제된다.

LLM이 없거나 실패하면 같은 컨텍스트를 규칙 기반으로 읽어서 답한다. 덕분에 키
없이도, 오프라인에서도 챗봇이 동작한다. 시연할 때 이게 꽤 중요했다.

`LLM_PROVIDER` 값만 바꾸면 gemini ↔ ollama ↔ rule을 코드 수정 없이 갈아끼운다.

### 경영용어 툴팁

화면에 안전재고, ROP, 회전율 같은 SCM 용어가 그대로 뜨는데 비전공 실무자는 이걸
모른다. `?` 아이콘에 마우스를 올리면 정의와 계산식이 나오게 했다.

용어 정의는 `backend/app/data/glossary.py` 한 파일에서만 관리하고 `/api/glossary`로
내려보낸다(35개, 6개 카테고리). 툴팁·용어집 화면·챗봇 답변이 전부 같은 데를 보기
때문에, 설명을 고칠 때 HTML을 건드릴 일이 없다.

## 9. 화면

React 단일 HTML이다. 빌드 도구를 안 쓴다. 상단 바에 탭 여섯 개(KPI, Odoo 실재고,
NFC 입출고, 설비 유지보수, 운영 관리, 용어집)와 우측 하단에 챗봇이 있다.

디자인은 Odoo 톤(보라 #714B67, 밝은 회색 바탕, 리스트뷰 테이블)에 맞췄다. Odoo를
옆 탭에 띄워놓고 왔다 갔다 하는데 색이 따로 놀면 어색하다.

상단 상태 배지가 1분마다 `/api/ops/health`를 찔러서, 어느 화면에 있든 시스템
이상을 알 수 있다.

NFC 입출고는 현장 입력이라 항상 운영계(Odoo)로만 보낸다.

## 10. 인프라

Docker Compose 스택 세 개(StockCast, Odoo, Caddy)로 나눠 띄운다. Terraform으로
VPC·보안그룹(22/80/443/8000/8069)·EC2(t4g.small)·Elastic IP·RDS를 정의했다.
8000과 8069는 기본으로 내 IP에서만 열린다.

t3.micro(1GB)에서는 Odoo가 안 떠서 2GB에 스왑 2GB를 붙였다.
지금은 같은 2GB인 t4g.small(ARM)이라 월 $3.80이 덜 든다. 인스턴스를
바꾸면 IP가 변하는 바람에 Elastic IP로 고정했다. 안 쓸 때 인스턴스를 중지하면
컴퓨팅 과금은 0이고 주소는 유지된다.

로컬에서 쓰던 `docker compose`를 EC2에서도 그대로 쓴다. "로컬에선 됐는데 서버에선
안 되네"를 없애려는 의도였고 실제로 효과가 있었다.

HTTPS는 Caddy + DuckDNS 조합이다. Web NFC가 HTTPS를 요구해서 필수였다.

### CI/CD

`ci.yml`은 main/PR 푸시마다 pytest 75건을 돌린다. SQLite 인메모리라 외부 DB나
키가 필요 없다. `deploy.yml`은 `workflow_call`로 ci.yml을 재사용해서 테스트가
통과해야만 EC2에 SSH 배포하고, 배포 후 `/api/ops/health`로 실제로 떴는지 확인한다.

## 11. 보안·비밀값

| 막은 것 | 방법 |
|---------|------|
| 키가 깃에 올라가는 것 | `.env`·`*.tfvars`·`*.tfstate`를 gitignore, 코드는 `settings`로만 읽는다 |
| 설정이 갈리는 것 | `.env`는 저장소 루트 하나만 본다(`config.REPO_ROOT`) |
| 외부 노출 | 운영 접속은 HTTPS만, SSH는 내 IP만 |
| 키 없을 때 터지는 것 | 외부 키가 없으면 수집을 건너뛰고 규칙 폴백으로 간다 |

`.env`가 루트와 `backend/` 양쪽에 있었을 때 실행 위치에 따라 설정이 갈리는 문제를
겪었다. 그래서 루트 하나로 통일했다.

운영 단계까지 간다면 `.env`를 AWS Secrets Manager로 옮기는 게 맞다.

## 12. 테스트

pytest 75건, 전부 SQLite 인메모리로 돈다.

통합 테스트로 잡은 것들: 시드 FK 위반, 예측 NaN 직렬화 실패, 수집 중단, 공휴일
PK 충돌. 설비 모듈에서는 정비 완료 시 재고 차감, 재고 부족 시 409 거부, 중복 완료
거부를 테스트로 고정했다.

`backend/tests/conftest.py`가 app을 import 하기 전에 `DATABASE_URL`과 외부 키를
못박는다. 이게 없었을 때 개발자 로컬 `.env`나 CI 기본값에 따라 테스트가 실제 DB에
붙으려다 실패했다.

## 13. 한계

수요가 모델 생성치라는 게 제일 큰 한계다. 실 판매 트랜잭션이 없다.

현재고의 정답은 Odoo이고 StockCast DB는 분석용이라 실시간으로 완전히 동기화되지는
않는다. 역방향 조회로 대신하고 있다.

인증·권한과 감사로그가 없다. PoC 범위라고 넘어갔지만 운영이면 필요하다. 단일
EC2라 인스턴스가 죽으면 전부 멈추는 것도 문제다.

개선한다면 POS나 주문 데이터를 연동해 수요를 실측하고, RDS로 분리해 Multi-AZ를
쓰고, RBAC와 Secrets Manager를 붙이는 순서로 갈 것 같다. 예측 쪽은 외생변수를
더 넣고 백테스트를 자동화하는 게 남았다.
