# 시스템 아키텍처

공공조달 납품업체가 쓰는 재고관리·수요예측 백오피스다. 실물 재고는 Odoo가 맡고,
분석은 StockCast가 맡는다. 둘을 API로 연결했다.

---

## 1. 전체 구성

```mermaid
flowchart TB
    subgraph EXT["외부 공공데이터"]
        KMA["기상청 ASOS<br/>일 기온·강수"]
        HOL["특일정보<br/>공휴일"]
        NARA["나라장터<br/>입찰공고"]
        PPS["조달청 MAS<br/>계약단가"]
    end

    subgraph CLIENT["사용자"]
        PHONE["안드로이드 폰<br/>Web NFC 태깅"]
        BROWSER["관리자 브라우저"]
    end

    subgraph EDGE["엣지 (HTTPS)"]
        CADDY["Caddy 리버스 프록시<br/>Let's Encrypt 자동 발급"]
    end

    subgraph APP["StockCast — 분석계"]
        API["FastAPI<br/>13개 라우터"]
        ANALYTICS["분석 엔진<br/>OLS · Holt-Winters · SARIMA<br/>안전재고 · ROP · ABC"]
        LLM["LLM 어댑터<br/>Gemini / Ollama / 규칙"]
        PG[("PostgreSQL 16<br/>18개 엔터티<br/>1년 거래이력 + 외부데이터")]
    end

    subgraph ERP["Odoo 18 — 운영계"]
        ODOO["Odoo Community<br/>재고·입출고·재주문규칙"]
        ODOOPG[("Odoo 전용<br/>PostgreSQL")]
    end

    PHONE --> CADDY
    BROWSER --> CADDY
    CADDY --> API
    KMA & HOL & NARA & PPS -.수집 커넥터.-> API
    API <--> PG
    API <--> ANALYTICS
    ANALYTICS --> PG
    API <--> LLM
    API -- "정방향: ROP·발주상한<br/>역방향: 실재고 조회<br/>XML-RPC" --> ODOO
    ODOO <--> ODOOPG
```

DB가 두 개인 게 눈에 띌 텐데, 이유가 세 가지 있다.

첫째로 날씨·공휴일·입찰·단가 같은 외부 데이터는 ERP에 넣을 자리가 없다. 그런데
수요예측은 "그날 출고량 × 그날 기온"을 조인해야 나온다.

둘째로 무거운 분석 쿼리를 실시간 운영 DB에 돌리면 창고 입출고가 느려진다. 창고
직원이 물건 찍는데 화면이 멈추면 안 된다.

셋째로 매번 Odoo에서 1년치를 XML-RPC로 끌어와 회귀를 돌리면 너무 느리다.

결국 OLTP와 OLAP를 나누는 흔한 방식으로 갔다.

## 2. 입출고가 재고를 만든다

```mermaid
sequenceDiagram
    actor W as 창고 직원
    participant F as NFC 화면
    participant A as StockCast API
    participant D as StockCast DB
    participant O as Odoo (운영계)

    W->>F: NFC 태그 스캔
    F->>A: POST /api/odoo/nfc-scan
    A->>D: 태그 UID → 자재·저장위치 해석
    A->>O: stock.quant 수량 갱신 (XML-RPC)
    O-->>A: 갱신 후 실재고
    A-->>F: 처리 결과
    Note over A,O: NFC는 현장 입력이라<br/>운영계(Odoo)로만 보낸다
```

NFC 스캔은 실물이 실제로 움직이는 사건이니까 운영계로 바로 간다. 반면 수기 입력이나
정비 부품 소비는 분석계에서 자재문서로 처리한다.

```mermaid
flowchart LR
    IN["입력<br/>수기 / 정비 소비 / 시드"] --> DOC["자재문서 전기<br/>헤더 1건 + 항목 N건"]
    DOC --> MVT{"이동유형<br/>방향"}
    MVT -->|"+1 (101·561)"| UP["재고 증가"]
    MVT -->|"−1 (201·261)"| DOWN["재고 감소<br/>부족하면 409로 거부"]
    UP & DOWN --> STOCK[("stock<br/>unrestricted_qty")]
    DOC --> HIST["출고 이력<br/>= 수요 시계열"]
    HIST --> FC["수요예측"]
```

여기서 `Σ(방향 × 수량) = 재고` 라는 등식이 나온다. 재고를 직접 UPDATE 하지 않기
때문에 항상 성립해야 하고, 안 맞으면 어딘가 잘못된 것이다. 운영 화면의 정합성
점검 C01이 이걸 계속 본다.

## 3. 분석 파이프라인

```mermaid
flowchart LR
    subgraph SRC["입력"]
        A1["출고 이력<br/>이동유형 201"]
        A2["날씨·공휴일<br/>외부 공공데이터"]
    end
    A1 & A2 --> FEAT["피처 생성<br/>build_features()<br/>날짜로 조인"]
    FEAT --> REG["다중회귀 OLS<br/>기온·강수·주말·공휴일"]
    FEAT --> TS["시계열<br/>Holt-Winters / SARIMA"]
    FEAT --> STAT["일수요 통계<br/>평균 d̄ · 표준편차 σ"]
    STAT --> INV["안전재고 SS = Z·σ·√L<br/>재주문점 ROP = d̄·L + SS<br/>발주상한 S = d̄·(L+R) + SS"]
    REG --> DEC["의사결정"]
    TS --> DEC
    INV --> DEC
    INV -->|"write-back"| ODOO["Odoo 재주문 규칙"]
    DEC --> KPI["KPI · ABC · AI 요약"]
```

회귀를 쓴 건 정확도보다 해석 때문이다. 계수를 보면 "기온이 1℃ 내려가면 제설제
출고가 1.6개 늘어난다" 같은 문장이 그대로 나오고, 이게 발주 근거가 된다.
시계열은 날씨 예보를 못 구할 때를 위한 보완책이다. 외부 변수 없이도 돌아간다.

## 4. Odoo 연동

```mermaid
flowchart LR
    subgraph SC["StockCast (분석계)"]
        ROP["재주문점·발주상한"]
        DASH["대시보드"]
        NFCS["NFC 스캔"]
    end
    subgraph OD["Odoo 18 (운영계 · system of record)"]
        OP["stock.warehouse.orderpoint<br/>재주문 규칙"]
        QT["stock.quant<br/>실물 재고"]
        PR["product.product<br/>품목 마스터"]
    end
    ROP -->|"정방향 write<br/>odoo_sync_reorder.py"| OP
    QT -->|"역방향 read<br/>/api/odoo/stock"| DASH
    NFCS -->|"입고+/출고−"| QT
    PR -.->|"적재 odoo_load.py"| PR
```

Odoo DB에 직접 붙는 게 빠르긴 하지만 그렇게 하지 않았다. Odoo가 가진 검증 로직을
통째로 건너뛰게 되기 때문이다. XML-RPC는 공식 인터페이스라 버전이 올라가도
계약이 유지된다. 참고로 Odoo 온라인 무료판은 외부 API가 막혀 있어서 Docker로
직접 띄웠다.

## 5. AWS 배포

```mermaid
flowchart TB
    USER["사용자"] -->|HTTPS 443| DNS["DuckDNS<br/><내도메인>.duckdns.org"]
    DNS --> EIP["Elastic IP<br/>중지·재시작해도 주소 유지"]

    subgraph VPC["AWS VPC (기본) · ap-northeast-2"]
        subgraph SG["보안그룹 — 22는 내 IP만"]
            subgraph EC2["EC2 t4g.small (2GB + 스왑 2GB)"]
                subgraph S1["docker-compose.yml"]
                    BE["backend<br/>FastAPI :8000"]
                    DB[("db<br/>PostgreSQL :5432")]
                end
                subgraph S2["infra/odoo"]
                    OD["odoo :8069"]
                    ODB[("odoo_db")]
                end
                subgraph S3["infra/caddy"]
                    CD["caddy :80/:443"]
                end
            end
        end
    end

    EIP --> CD
    CD --> BE
    BE <--> DB
    BE <-->|host.docker.internal| OD
    OD <--> ODB
```

인프라는 Terraform으로 짰다. 콘솔에서 클릭하면 나중에 뭘 어떻게 만들었는지
재현이 안 되고, 인스턴스 타입을 바꾸거나 포트를 열 때마다 손이 간다.

t3.micro로 시작했다가 Odoo가 안 떠서 2GB로 올렸다. 지금은 같은 2GB인 t4g.small(ARM)을 쓴다.
Odoo 권장 사양이 2GB
이상인데 micro는 1GB다. 스왑도 2GB 붙였다. 인스턴스 타입을 바꾸면 공인 IP가
바뀌는 바람에 도메인이 끊겨서 Elastic IP로 고정했다.

HTTPS는 Caddy가 Let's Encrypt 인증서를 알아서 받아온다. 이게 필요한 이유는
Web NFC가 보안 컨텍스트에서만 동작하기 때문이다. HTTP로는 폰 태깅이 아예 안 된다.

스택을 셋으로 나눈 건 Odoo가 전용 PostgreSQL을 요구하고, Caddy는 앱과 생명주기가
다르기 때문이다.

## 6. 배포 파이프라인

```mermaid
flowchart LR
    DEV["git push<br/>main"] --> CI["ci.yml<br/>pytest 75건<br/>SQLite 인메모리"]
    CI -->|통과| DEPLOY["deploy.yml<br/>workflow_call 재사용"]
    CI -->|실패| STOP["배포 중단"]
    DEPLOY --> SSH["EC2 SSH<br/>git pull<br/>docker compose up -d --build"]
    SSH --> HC["/api/ops/health<br/>기동 검증"]
    HC -->|healthy·degraded| OK["배포 완료"]
    HC -->|타임아웃| FAIL["배포 실패 처리"]
```

테스트가 외부 DB나 API 키에 의존하지 않는 게 중요하다. `backend/tests/conftest.py`가
app을 import 하기 전에 `DATABASE_URL`과 외부 키를 고정해버려서, 어느 환경에서
돌리든 SQLite 인메모리로 간다.

## 7. 계층별 기술 스택

| 계층 | 기술 | 역할 |

## 8. 운영 상태를 어떻게 보는가

운영 기능을 앱 안에 넣었다. SSH로 들어가서 로그를 tail 하지 않고 브라우저에서 본다.

```mermaid
flowchart LR
    REQ["모든 HTTP 요청"] --> MW["RequestLogMiddleware<br/>경로·상태·소요시간"]
    MW --> RB[("메모리 링버퍼<br/>최근 500건")]
    RB --> LOGS["/api/ops/logs<br/>오류만 · 느린요청만"]

    HEALTH["/api/ops/health"] --> C1["DB SELECT 1"]
    HEALTH --> C2["Odoo XML-RPC 인증"]
    HEALTH --> C3["LLM 가용성"]
    HEALTH --> C4["디스크·메모리·Load"]
    HEALTH --> ST{"healthy<br/>degraded<br/>down"}
    ST --> UI["대시보드 상태 배지<br/>1분마다 갱신"]
    ST --> AUTO["자동 복구 스크립트<br/>down이면 재기동"]

    INTEG["/api/ops/integrity"] --> CK["정합성 9항목<br/>C01 Σ(방향×수량)=재고"]
```

`/api/ops/health` 하나를 사람과 기계가 같이 쓴다. 화면에 뜨는 신호랑 자동 복구가
보는 신호가 다르면, 화면은 멀쩡한데 서버는 죽어 있는 상황이 생긴다.

## 9. 지금의 한계

| 현재 | 다음 단계 | 이유 |
| :--- | :--- | :--- |
| 단일 EC2에 DB 동거 | RDS 분리 · Multi-AZ | 백업·가용성을 관리형에 맡긴다 |
| 메모리 링버퍼 로그 | CloudWatch Logs | 재시작하면 로그가 날아간다 |
| 수동 헬스체크 | ALB 헬스체크 + Auto Scaling | 죽으면 자동 교체 |
| `.env` 파일 | AWS Secrets Manager | 키 회전·감사 |
| 인증 없음 | RBAC로 `/api/ops/*` 보호 | 운영 API가 열려 있다 |
| 수요는 모델 생성치 | POS·주문 실거래 연동 | 예측 정확도 |
