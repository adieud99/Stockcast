# 서버 자동 복구

서버가 죽었을 때 사람이 붙기 전에 스스로 돌아오게 한다.

## 원래 상태의 구멍

손대기 전에 무엇이 안 되는지부터 봤다.

| 상황 | 원래 | 왜 |
|---|---|---|
| 컨테이너가 죽음 | **안 살아남** | `docker-compose.yml` 에 `restart` 정책이 없었다 |
| EC2 재부팅 | **아무것도 안 뜸** | `user_data` 는 인스턴스를 처음 만들 때 한 번만 돈다 |
| 앱이 살아는 있는데 응답 없음 | **모름** | 아무도 안 본다 |
| 호스트 하드웨어 장애 | 부분적 | AWS 기본 복구에 기대고 있었다 |
| 디스크 참 | **모름** | 지표를 안 올리고 있다 |

제일 큰 건 두 번째다. 재부팅 한 번이면 서비스가 그대로 멈춘 채로 있는다.

## 방안 비교

| 방안 | 막아 주는 고장 | 비용 | 골랐나 |
|---|---|---|---|
| `restart: unless-stopped` | 컨테이너 프로세스 죽음 | 0 | **O** |
| systemd 유닛 등록 | 재부팅 후 미기동 | 0 | **O** |
| 헬스 워치독 타이머 | 앱이 멈춰 응답 없음 | 0 | **O** |
| CloudWatch `StatusCheckFailed_System` → recover | 호스트 하드웨어·전원 장애 | 알람 10개까지 무료 | **O** |
| CloudWatch `StatusCheckFailed_Instance` → reboot | 커널 패닉, OS 손상 | 〃 | **O** |
| 디스크 사용률 알람 | 볼륨 참 | 〃 (에이전트 필요) | O(알림만) |
| Auto Scaling Group min=max=1 | 인스턴스 통째 소실 | ASG 자체는 무료 | X |
| Route 53 헬스체크 + 장애조치 | 리전 단위 장애 | 유료 | X |
| RDS Multi-AZ | DB가 있는 AZ 장애 | DB 요금 2배 | X |

ASG 를 뺀 이유는 이 구성과 안 맞아서다. 인스턴스가 교체되면 EBS 볼륨이 새로 만들어져서
컨테이너 볼륨에 있던 데이터가 사라진다. DB를 RDS로 빼기 전에는 ASG 가 오히려 위험하다.
Route 53 과 Multi-AZ 는 비용이 목적에 비해 크다. 학습·포트폴리오용 서버 한 대에
리전 장애 대비를 붙일 이유가 없다.

## 넣은 것

### 1. 컨테이너 재시작 정책

`docker-compose.yml` 의 `db` 와 `backend` 에 `restart: unless-stopped` 를 넣었다.
`odoo` 와 `caddy` 에는 원래 있었는데 정작 본체에 빠져 있었다.

`always` 가 아니라 `unless-stopped` 인 이유는, 사람이 일부러 내린 걸
도커가 다시 올리면 안 되기 때문이다.

### 2. 부팅 시 자동 기동

`infra/systemd/stockcast.service` 를 `/etc/systemd/system/` 에 넣고 enable 한다.
`user_data` 가 인스턴스를 만들 때 알아서 등록한다.

RDS를 쓰는지에 따라 compose 파일 조합이 달라져서, `user_data` 가 `ExecStart` 줄을
그때그때 고쳐서 설치한다.

```bash
systemctl status stockcast
systemctl restart stockcast
```

### 3. 헬스 워치독

`infra/scripts/watchdog.sh` 를 2분마다 돌린다(`stockcast-watchdog.timer`).
프로세스는 살아 있는데 응답을 안 하는 경우를 잡는다. 재시작 정책으로는 안 잡힌다.

단계적으로 올라간다.

| 연속 실패 | 하는 일 | 왜 |
|---|---|---|
| 1회 | `backend` 컨테이너만 재시작 | 빠르고 영향이 작다 |
| 2회 | compose 전체 재기동 | 컨테이너 하나로 안 풀린 경우 |
| 3회 이상 | **아무것도 안 하고 로그만 남긴다** | 계속 재시작하면 로그가 덮여 원인을 못 본다 |

여기에 더해 **한 시간에 4번**까지만 조치한다. 고장이 안 풀리는데 2분마다 껐다 켜면
상황만 나빠진다. 상한에 걸리면 자동 복구를 멈추고 사람을 기다린다.

얕은 `/health` 를 쓴다. `/api/ops/health` 는 DB·Odoo·LLM 까지 확인하는데,
그걸 재시작 기준으로 삼으면 RDS 가 잠깐 느려질 때마다 앱을 껐다 켜게 된다.
깊은 쪽은 상태를 보는 용도지 되살리는 기준이 아니다.

로그는 `/var/log/stockcast-watchdog.log` 에 쌓인다.

```bash
journalctl -u stockcast-watchdog.service -n 50
tail -f /var/log/stockcast-watchdog.log
systemctl list-timers stockcast-watchdog.timer
```

### 4. CloudWatch 알람

`infra/terraform/autorecovery.tf` 에 두 개를 만든다.

`StatusCheckFailed_System` 은 AWS 쪽 문제다. 호스트 하드웨어나 전원, 네트워크가
나간 경우라 인스턴스를 다른 하드웨어로 옮겨야 한다. `ec2:recover` 가 그 일을 한다.
인스턴스 ID·공인 IP·EBS 볼륨은 유지된다.

솔직히 말하면 **이 복구는 요즘 AWS가 기본으로 해 준다**(simplified automatic recovery).
그래서 이 알람의 실제 값어치는 복구 자체보다 "언제 무슨 일이 있었는지 기록에 남는다"에 있다.

`StatusCheckFailed_Instance` 는 인스턴스 안 문제다. 커널이 멈췄거나 파일시스템이
깨진 경우로, 재부팅으로 푼다. **이건 기본 동작이 아니라서 실제로 추가되는 안전장치다.**

둘 다 1분 간격으로 보되 연속 2회(recover) / 3회(reboot) 실패해야 움직인다.
재부팅은 서비스가 끊기니 한 단계 더 느슨하게 뒀다.

## 복구가 안 되는 것

자동으로 못 고치는 것을 분명히 해 둔다.

- **데이터 손상.** 잘못된 데이터가 들어간 건 재시작으로 안 고쳐진다. 백업에서 되돌려야 한다
- **디스크 참.** 알람만 울린다. 로그와 도커 이미지를 지우는 건 사람이 판단할 일이다
  (`docker system prune` 은 쓰던 이미지까지 지울 수 있다)
- **설정 실수.** 잘못된 `.env` 로 뜬 앱은 헬스체크를 통과할 수도 있다
- **인스턴스 종료(terminate).** ASG 를 안 썼으니 다시 만들어야 한다.
  `terraform apply` 로 복구하되, 컨테이너 볼륨에 있던 데이터는 사라진다.
  이게 DB를 RDS로 빼면 좋은 이유 중 하나다

## 만들면서 고친 것

처음 짠 대로 뒀으면 운영에서 터졌을 것들이다.

**워치독이 RDS 모드를 몰랐다.** `user_data` 는 compose 파일 조합을 `COMPOSE_ARGS`
라는 이름으로 남기는데 워치독은 `COMPOSE_FILES` 를 읽었고, 워치독 유닛이 그 파일을
읽지도 않았다. 그대로 두면 RDS 모드에서 복구가 돌 때 base 파일만 보고
`compose up -d --force-recreate` 를 해서, **있으면 안 되는 로컬 Postgres 컨테이너를
새로 만든다.** 앱은 RDS 를 보고 있는데 옆에 빈 DB 가 하나 더 뜨는 상태가 된다.
이름을 `COMPOSE_FILES` 로 맞추고 유닛에 `EnvironmentFile=-/etc/stockcast.env` 를 넣었다.

**초기 시드가 옮긴 데이터를 지울 수 있었다.** `user_data` 가 `collect_real_data.py` 를
돌렸는데 이 스크립트는 `drop_all()` 부터 한다. RDS 로 데이터를 옮겨 두고 EC2 를
새로 만들면 그걸 통째로 날린다. 지금은 테이블 수를 먼저 세고 **비어 있을 때만**
`init_db.py` 를 돌린다. `init_db.py` 는 `create_all` 만 하고 데이터가 있으면 건너뛴다.

## 확인해 본 것

워치독은 실제로 앱을 띄워 놓고 죽여 가며 확인했다.

| 확인 | 결과 |
|---|---|
| 정상일 때 아무것도 안 함 | 종료코드 0, 실패 카운터 0 |
| 1회 실패 | `compose restart backend` 호출 |
| 2회 실패 | `compose up -d --force-recreate` 호출 |
| 3회 실패 | 아무 호출 없이 로그만 |
| 시간당 상한 초과 | docker 호출 0회, "사람 확인을 기다린다" 로그 |
| 복귀 | "정상 복귀 (직전 연속 실패 N회)" 로그 |

여기서 한 가지를 더 봤다. `docker kill` 로 컨테이너를 죽이면 워치독이 살리긴 하는데,
**그건 `restart: unless-stopped` 도 하는 일이라 워치독의 값어치를 증명하지 못한다.**

그래서 재시작 정책이 못 고치는 상황으로 다시 확인했다. `docker pause` 로 컨테이너를
얼리면 프로세스는 살아 있고 상태도 정상이라 도커가 손대지 않는다. 30초를 기다려도
`paused` 그대로였고 `/health` 는 무응답이었다. 워치독을 돌리니 `running` 으로 돌아오고
`/health` 가 첫 시도에 응답했다. **이게 워치독이 있어야 하는 이유다.**

### systemd 도 실제로 돌려 봤다

EC2 에 올리는 대신 **Amazon Linux 2023 arm64 컨테이너에 systemd 를 PID 1 으로 띄워서**
확인했다. 실제 배포 대상과 같은 OS·아키텍처다.

| 확인 | 결과 |
|---|---|
| 유닛 파일 문법 (`systemd-analyze verify`) | 3개 모두 오류 없음 |
| `ExecStart` 경로 | AL2023 의 docker 는 `/usr/bin/docker`. 유닛과 일치 |
| 타이머 등록 | `enable --now` 로 심볼릭 링크 생성, 3분 뒤로 예약됨(`OnBootSec=3min`) |
| `EnvironmentFile` | `/etc/stockcast.env (ignore_errors=yes)` 로 읽힘. `-` 접두사가 동작한다 |
| 서비스 실행 | 스크립트가 돌고 로그가 journald 에 남았다. 1단계 에스컬레이션까지 진입 |
| `TriggeredBy` 연결 | 서비스 상태에 타이머가 표시됨 |
| **실패해도 계속 도는가** | **2분 간격으로 6회 실행. 매번 실패했는데도 타이머는 `active`** |

마지막 줄이 제일 중요하다. 워치독 서비스는 앱이 죽어 있으면 종료코드 1로 끝난다.
oneshot 유닛이 실패하면 `systemctl --failed` 에 잡히고 시스템 상태가 `degraded` 가 되는데,
**타이머는 그와 무관하게 계속 돈다.** 한 번 실패했다고 감시가 멈추면 그게 더 큰 문제다.

여전히 확인 못 한 것은 `user_data` 전체를 실제 EC2 부팅으로 돌려 보는 것과,
CloudWatch 알람이 실제 장애에 반응하는지다. 알람은 `terraform plan` 으로
만들어지는 것까지만 봤다.
