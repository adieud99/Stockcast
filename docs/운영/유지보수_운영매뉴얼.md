# 유지보수·운영 매뉴얼

이 시스템을 혼자 돌리는 데 필요한 것만 모았다. 뭘 확인하고, 문제가 생기면 뭘
누르는지가 기준이다.

여기서 다루는 건 시스템 운영이다. 물류센터 설비 정비를 관리하는 기능(제품 기능)은
7절에 요약만 해뒀다.

---

## 1. 정기 점검

| 주기 | 확인할 것 | 어디서 | 정상이면 |
|:---|:---|:---|:---|
| 매일 | 시스템 상태 | 대시보드 상단 배지 또는 운영 관리 → 상태 점검 | `정상` |
| 매일 | 요청 오류율 | 운영 관리 → 상태 점검 | 0~1% |
| 매일 | 예방정비 지연 | 설비 유지보수 → 예방정비 일정 | 지연 0건 |
| 매주 | 데이터 정합성 | 운영 관리 → 데이터 정합성 | 위험 0건 |
| 매주 | 외부 데이터 최신성 | 운영 관리 → 적재 현황 | 날씨 7일 이내 |
| 매주 | 디스크 사용률 | 운영 관리 → 상태 점검 | 85% 미만 |
| 매월 | 백업 복원 시험 | 5절 | 복원 성공 |

상단 배지가 노란색(`일부 저하`)이면 Odoo 연동만 끊긴 상태라 분석과 예측은 계속
돌아간다. 빨간색(`장애`)이면 DB가 죽은 거라 바로 4절로 간다.

---

## 2. 상태 점검이 보는 것

`GET /api/ops/health` 하나로 다 본다. 로그인 없이 부르면 판정(`status`)만 주고,
로그인하면 구성요소·자원까지 준다. 워치독은 더 얕은 `/health` 로 생사만 본다.

```bash
TOKEN=$(STOCKCAST_URL=https://<내도메인>.duckdns.org python3 scripts/api_token.py)
curl -s -H "Authorization: Bearer $TOKEN" https://<내도메인>.duckdns.org/api/ops/health \
  | jq '.status, .components'
```

| status | 뜻 | 뭘 하나 |
|:---|:---|:---|
| `healthy` | 다 정상 | 없음 |
| `degraded` | Odoo만 끊김, 분석은 정상 | 4-B |
| `down` | DB 연결 불가, 서비스 정지 | 4-A (자동 재기동 대상) |

구성요소별로는 이렇게 판단한다.

**database** — `SELECT 1` 왕복 시간을 잰다. `latency_ms`가 평소의 10배쯤 되면
DB에 부하가 걸린 걸 의심한다.

**odoo** — XML-RPC 인증까지 시도한다. `configured:false`는 키를 안 넣은 상태라
장애가 아니다.

**llm** — 키와 응답을 확인한다. 실패해도 규칙 기반 폴백이 있어서 서비스 자체는
정상이다.

## 3. 데이터 정합성 점검

운영 관리 → 데이터 정합성, 또는 `GET /api/ops/integrity`. 각 항목은 뭐가 틀렸는지,
뭘 해야 하는지, 실제 위반 샘플까지 같이 준다.

| 코드 | 점검 | 심각도 | 걸리면 |
|:---|:---|:---|:---|
| C01 | 자재문서 합계 = 재고 수량 | 위험 | 이동 없이 재고가 바뀌었다. 수기 UPDATE나 연동 오류 |
| C02 | 음수 재고 없음 | 위험 | 출고 검증을 우회한 전기가 있었다 |
| C03 | 고아 참조 없음 (자재문서→자재) | 위험 | 자재 마스터가 지워졌다 |
| C04 | 재주문점 ≥ 안전재고 | 주의 | ROP 계산이 낡았다. `/api/reorder/apply` 재실행 |
| C05 | 모든 자재에 NFC 태그 | 정보 | 현장에서 스캔 입출고를 못 한다 |
| C06 | 외부 날씨 7일 이내 | 주의 | 수집 스케줄이 죽었다. 6절 참고 |
| C07 | 완료 정비오더 부품이 전기됨 | 주의 | 부품이 장부 없이 사라졌다 |
| C08 | 예방정비 지연 없음 | 주의 | 곧 고장으로 이어진다 |
| C09 | 모든 자재에 재고 레코드 | 정보 | 출고가 안 되고 KPI 집계에서 빠진다 |

C01이 제일 중요하다. 이 시스템에서 재고는 직접 고치는 값이 아니라 이동유형
방향(±1)×수량을 누적한 결과여야 한다. 이게 어긋났다면 다른 지표도 믿을 수 없다.

## 4. 장애 대응

### A. 서비스가 안 뜬다 (status=down)

서버에서는 `docker compose` 를 맨손으로 치지 말고 `make` 를 쓴다.
RDS 모드면 compose 파일이 두 개인데, base 하나만 쓰면 접속 주소가
`@db:5432` 로 덮여서 **앱이 RDS 를 버리고 빈 컨테이너 DB 를 보게 된다.**
`make` 가 `/etc/stockcast.env` 를 읽어 알아서 맞춘다.

```bash
ssh -i <키>.pem ec2-user@<EIP>
cd /opt/stockcast
make ps                                # 뭐가 죽었나
make logs                              # 원인 확인 (Ctrl+C 로 빠져나온다)
sudo systemctl restart stockcast       # 재기동
curl -s localhost:8000/api/ops/health | jq .status
```

워치독이 2분마다 돌고 있으니, 손대기 전에 이미 한 번 살려 봤을 수 있다.
무엇을 했는지 먼저 본다.

```bash
tail -30 /var/log/stockcast-watchdog.log
```

로그에 "상한에 걸렸다"가 있으면 자동 복구가 멈춘 상태다. 원인을 고친 뒤
카운터를 지워야 다시 돈다.

```bash
sudo rm -f /var/lib/stockcast/consecutive_failures /var/lib/stockcast/recent_actions
```

그래도 안 되면 볼륨은 건드리지 말고 재빌드한다.

```bash
make up
```

`docker compose down -v`는 **컨테이너 DB 모드에서 DB 볼륨을 지운다.**
백업 없이 절대 쓰면 안 된다. RDS 모드에서는 DB가 인스턴스 밖에 있어서
이 명령으로는 안 지워지지만, 그렇다고 습관을 들일 명령은 아니다.

### B. Odoo 연동이 끊겼다 (status=degraded)

```bash
cd /opt/stockcast/infra/odoo
docker compose -f docker-compose.odoo.yml ps
docker compose -f docker-compose.odoo.yml up -d
python scripts/odoo_ping.py            # 인증 확인
```

Odoo는 메모리를 꽤 먹는다. 2GB에서 OOM으로 죽었다면 스왑부터 확인한다.
`free -h`에서 스왑이 0이면 8절을 본다.

### C. 응답이 느리다

1. 운영 관리 → 요청 로그 → 느린 요청 탭에서 어떤 경로가 느린지 본다.
2. `/api/forecast`와 `/api/reorder`는 원래 무겁다. 전 품목 회귀를 돌리니까
   1~3초는 정상이다.
3. 전 구간이 느리면 `docker stats`로 CPU와 메모리를 본다.

### D. HTTPS 인증서 오류

```bash
cd /opt/stockcast/infra/caddy
docker compose -f docker-compose.caddy.yml logs --tail=50
docker compose -f docker-compose.caddy.yml restart
```

DuckDNS에 등록된 IP가 지금 EIP와 다르면 갱신이 실패한다. DuckDNS 대시보드에서
IP를 맞춰준다.

## 5. 백업과 복원

분석계 DB를 RDS로 옮긴 뒤로는 방식이 갈린다. 어느 쪽으로 돌고 있는지 먼저 본다.

```bash
cat /etc/stockcast.env      # COMPOSE_FILES 에 rds.yml 이 있으면 RDS 모드
```

### RDS 모드일 때 (지금 구성)

자동 백업이 켜져 있다. `backup_retention_period = 7` 이라 7일치를 AWS가 알아서
보관하고, 그 안의 아무 시점으로나 되돌릴 수 있다(시점 복구).

```bash
# 지금 백업이 제대로 도는지
aws rds describe-db-instances --db-instance-identifier stockcast-db \
  --query 'DBInstances[].[BackupRetentionPeriod,LatestRestorableTime]' --output text
```

큰 작업 전에는 손으로 스냅샷을 하나 떠 둔다. 자동 백업은 7일이 지나면 사라진다.

```bash
aws rds create-db-snapshot --db-instance-identifier stockcast-db \
  --db-snapshot-identifier stockcast-db-$(date +%Y%m%d-%H%M)
```

파일 백업은 `stockcast-backup.timer` 가 매일 03:00 에 `scripts/backup.sh` 를 돌려
`/opt/backup` 에 쌓고 14일 지난 건 지운다. 손으로 돌릴 때는 이렇게 한다.
`db` 컨테이너가 없으므로 `docker compose exec -T db` 는 쓸 수 없다.

```bash
cd /opt/stockcast && sudo ./scripts/backup.sh            # --verify 를 붙이면 임시 DB 에 복원까지 해 본다
systemctl list-timers stockcast-backup.timer             # 다음 실행 시각
journalctl -u stockcast-backup --since today             # 오늘 결과
```

`.env` 를 `. .env` 로 source 하면 안 된다. `RDS_DATABASE_URL_PSYCOPG` 값에 공백이 있어서
`host=...` 까지만 읽히고 비밀번호가 빠진다. 값이 필요하면 줄 단위로 꺼낸다.

```bash
CONN=$(sudo grep -E '^RDS_DATABASE_URL_PSYCOPG=' /opt/stockcast/.env | cut -d= -f2- | sed 's/^"//;s/"$//')
```

`pg_dump` 는 RDS 와 메이저 버전이 같아야 한다. `user_data` 가 설치하지만,
직접 깔았다면 `psql --version` 으로 확인할 것.

복원은 스냅샷에서 새 인스턴스를 만드는 쪽이 안전하다. 기존 것을 덮지 않는다.

```bash
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier stockcast-db-restore \
  --db-snapshot-identifier <스냅샷명>
# 확인 후 .env 의 RDS_DATABASE_URL 을 새 엔드포인트로 바꾸고 재기동
```

덤프 파일에서 되돌릴 때는 이렇게 한다.

```bash
# CONN 은 위에서 꺼낸 접속 문자열
gunzip -c /opt/backup/stockcast_2026-09-11_1156.sql.gz | psql "$CONN"
```

### 컨테이너 DB 모드일 때 (use_rds = false)

```bash
docker compose exec -T db pg_dump -U erp erp_nfc | gzip > /opt/backup/stockcast_$(date +%F).sql.gz
find /opt/backup -name 'stockcast_*.sql.gz' -mtime +14 -delete
```

복원.

```bash
gunzip -c /opt/backup/stockcast_2026-09-01.sql.gz | \
  docker compose exec -T db psql -U erp -d erp_nfc
```

### Odoo (두 모드 공통)

Odoo는 자기 Postgres 를 컨테이너로 계속 쓴다. RDS 로 안 옮겼다.

```bash
cd /opt/stockcast/infra/odoo
docker compose -f docker-compose.odoo.yml exec -T odoo_db \
  pg_dump -U odoo stockcast | gzip > /opt/backup/odoo_$(date +%F).sql.gz
```

복원해본 적 없는 백업은 백업이 아니다. 월 1회는 실제로 복원해보고, 복원 후
`/api/ops/integrity`가 정상으로 나오는지로 검증한다.

## 6. 정기 작업

| 작업 | 주기 | 누가 | 확인 |
|:---|:---|:---|:---|
| 외부 데이터 수집(날씨·공휴일·입찰·단가) | 매일 06:00 + 컨테이너 기동 시 | compose `scheduler` 서비스 | `docker logs erp_nfc_scheduler`, `logs/collect.log` |
| DB 파일 백업 | 매일 03:00 (꺼져 있던 날은 켜진 뒤) | `stockcast-backup.timer` | `journalctl -u stockcast-backup` |
| 헬스 워치독 | 2분 | `stockcast-watchdog.timer` | `/var/log/stockcast-watchdog.log` |
| 실데이터 전체 재수집 | 필요할 때 | 손으로 (`sudo make real`, 먼저 백업) | `make check` |
| 안전재고·ROP 재계산 | 주 1회 | 손으로 (대시보드 관리자 또는 아래) | 정합성 C04 |
| Odoo 재주문 규칙 반영 | 재계산 뒤 | 손으로 `odoo_sync_reorder.py` | Odoo 재고관리 → 재주문 규칙 |
| 이미지 정리 | 월 1회 | 손으로 `docker image prune -f` | |

수집 커넥터는 실패하면 1분·2분 뒤 두 번 더 시도하고, 끝까지 실패하면 로그에 남긴다.
서버에는 crontab 이 없다(AL2023). 주기 작업은 전부 컨테이너나 systemd 타이머로 건다.

```bash
# ROP 재계산은 관리자 토큰이 필요하다
TOKEN=$(python3 scripts/api_token.py)
curl -sX POST -H "Authorization: Bearer $TOKEN" localhost:8000/api/reorder/apply
```

## 7. 설비 유지보수 (제품 기능)

시스템 운영이 아니라 물류센터 설비 정비를 관리하는 화면이다.

설비 마스터에 지게차·컨베이어·항온항습기 같은 걸 등록해두고 상태(정상/점검중/
고장/폐기)와 정비주기를 관리한다. 예방정비 일정은 `최근 정비일 + 정비주기`로
다음 예정일을 계산하고, 지난 건은 지연으로 뜬다.

정비오더는 요청 → 진행 → 완료로 흐른다. 고장(CM)을 접수하면 설비가 자동으로
고장 정지가 돼서 가동률에 바로 반영된다.

완료 처리할 때 사용한 부품이 이동유형 261로 자재문서에 전기돼서 재고가 실제로
줄어든다. 재고가 부족하면 완료가 409로 막히기 때문에 장부와 실물이 어긋나지
않는다. 완료된 PM 오더는 설비의 최근 정비일을 갱신하고, 그러면 다음 주기가 다시
계산된다.

지표는 가동률, PM준수율, MTTR, 정비비용(인건비+부품)을 본다.

## 8. 서버 초기 설정 메모

스왑 2GB. 2GB 인스턴스에서 Odoo를 띄우려면 사실상 필수다. user_data가 자동으로 붙인다.

```bash
sudo dd if=/dev/zero of=/swapfile bs=128M count=16
sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

컨테이너에는 전부 `restart: unless-stopped`를 걸어뒀다. 호스트가 재부팅되거나
프로세스가 죽으면 Docker가 알아서 되살린다.

보안은 세 가지만 지킨다. SSH(22)는 보안그룹에서 내 IP만 열고, `.env`·
`terraform.tfvars`·`*.tfstate`는 깃에 안 올리고, 운영 접속은 HTTPS만 쓴다.

## 9. 자주 겪는 문제

| 증상 | 원인 | 해결 |
|:---|:---|:---|
| `/api/odoo/stock`이 `connected:false` | Odoo가 안 떴거나 키 미설정 | 4-B, `.env`의 `ODOO_*` 확인 |
| AI 요약이 계속 "규칙기반"으로 나옴 | LLM 키 없음 또는 네트워크 차단 | 정상 동작이다. LLM을 쓰려면 `.env`의 `LLM_PROVIDER`와 키를 설정 |
| C06 경고(날씨가 오래됨) | 수집기가 멈췄거나 키가 없다 | `docker logs erp_nfc_scheduler`, `logs/collect.log` 확인 |
| 로그인이 안 됨 | `.env` 의 `AUTH_*_PASSWORD` 가 비었다 | 값 넣고 backend 재기동. 서버는 SSM → `.env` |
| 로그인 실패 429 | 1분에 5번 넘게 틀렸다 | 1분 기다린다 |
| 서버 재부팅 후 Odoo 가 안 뜸 | Odoo DB 컨테이너 재시작 정책 누락(09-11 이전 서버) | `docker update --restart unless-stopped stockcast_odoo_db` |
| C04 경고 | 거래가 쌓였는데 ROP를 재계산 안 했다 | `POST /api/reorder/apply` |
| Web NFC가 안 됨 | HTTP로 접속했거나 iOS | HTTPS로 접속, 안드로이드 크롬 사용 |
| 대시보드가 빈 화면 | 시드를 안 넣었다 | `make seed` |
| 재기동 후 요청 로그가 비어 있음 | `LOG_DIR` 이 비었거나 `logs/` 에 쓸 수 없다 | 요청 기록은 `logs/requests.log` 에 남고 재기동 때 최근 500건을 되살린다 |

## 10. 규모가 커지면 바꿀 것

지금은 단일 EC2 PoC 기준이다.

| 지금 | 다음 | 이유 |
|:---|:---|:---|
| 메모리 링버퍼 로그 | CloudWatch Logs | 재시작해도 남고 검색·알람이 된다 |
